# Multi-worker live verification

On November 11, 2026, an isolated kind Kubernetes cluster exercised the controller-generated Zeek topology using synthetic traffic. This is a bounded development test, not a production deployment or a performance measurement.

The current operator manager reconciled a `KSensor` with `WorkerReplicas: 3`. It created manager, logger and proxy StatefulSets, a three-replica worker StatefulSet, and distinct worker Services. ZeekControl reported manager, logger, proxy, and workers `worker-001`, `worker-002`, and `worker-003` running. Three synthetic TCP client/server exchanges then targeted the three worker pod IPs separately. The centralized Zeek logger produced three JSON connection records, each with `conn_state: SF`, 18 originator bytes, 7 response bytes, and five packets in each direction. The three client source ports were 55100, 55101 and 55102; each destination was a different worker pod on port 53999. The payload was the synthetic string `YAS-SYNTHETIC-TEST` and the response was `YAS-ACK`.

The Zeek runtime was based on `zeek/zeek:lts` with a disposable validation adapter adding ZeekControl prerequisites: SSH server/client, rsync, tini, dumb-init, and a compatible filesystem layout. The SSH keypair was generated only for this test. Envoy and Prometheus sidecars were replaced by inert containers, so this exercise does not verify mesh transport or metrics. Traffic was injected directly into each worker's network interface; upstream capture distribution was not exercised. The test set `redef ignore_checksums = T;` in the site policy to accommodate container-network checksum offload. These settings should be assessed for the intended capture environment.

The checks uncovered and prompted fixes for the init shell condition, debug-mode SSH daemon exit, unsupported default policy imports and the ZeekControl non-shared spool setting. Kubernetes Pod readiness alone was not a sufficient proof of a running Zeek cluster: before these fixes, containers reported ready while ZeekControl deployment failed. Always inspect ZeekControl status and generated traffic logs during validation.

Local test-only artifacts for the session were written under `/tmp/yas-live`, including `zeekctl-three-worker-status.txt`, `zeek-three-worker-synthetic-connections.jsonl`, the synthetic capture generator, and the disposable adapter Dockerfiles. No production packet capture or private key is included in this repository.
